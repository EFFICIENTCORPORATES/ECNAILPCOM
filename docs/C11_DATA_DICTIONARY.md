# C11 — Data Dictionary
## Field-Level Governance, Definitions, Allowed Values, and Ownership for the Master Library

---

## 1. Objective

Provide a complete, authoritative reference for every field in the master compliance library. For each field, this dictionary specifies: its exact definition, its governance owner, the rules governing what values are acceptable, when the field is mandatory vs. optional vs. conditional, and how it must be populated.

The data dictionary is the single source of truth for field-level semantics. If a field's definition in this document conflicts with a comment in the database schema (doc 04) or the field descriptions in C1, this document governs — because this document carries the governance layer that the schema alone cannot express.

---

## 2. Why It Matters to the Compliance Engine

Ambiguous field definitions lead to inconsistent population. If two Library Populators have different understandings of what `consequence_summary` should contain, the field values become incomparable and the user-facing display becomes inconsistent. A data dictionary enforces shared semantics, making the library coherent regardless of who populates it or when.

Fields with governance ownership also have accountability. When a field is found to be incorrectly populated, the dictionary establishes who is responsible for its accuracy and what the correction procedure is.

---

## 3. Design Principles

**P1 — Every field has one definition.** No field may have ambiguous or context-dependent meaning. If a field's meaning varies by domain or obligation type, the variation must be documented explicitly in this dictionary.

**P2 — Governance ownership is field-level, not record-level.** The Library Populator populates the field, but the governance owner is responsible for its accuracy policy. The Library Owner is the default governance owner for all fields unless otherwise specified.

**P3 — Allowed values are exhaustive.** For enumerated fields, this dictionary lists every allowed value. No value outside the listed set may be used. If a new value is required, it must be added to this dictionary by the Library Owner before it can be used.

**P4 — Mandatory vs. optional is context-sensitive.** A field may be mandatory in some contexts (e.g., `applicable_states` is mandatory when `jurisdiction = SPECIFIC_STATES`) and optional in others. Conditional mandatory rules are explicitly documented.

---

## 4. Dictionary Format

Each field entry contains:

```
FIELD NAME
  Definition:      What this field means
  Layer:           MASTER (shared, law-level) or INSTANCE (per-business, computed)
  Mandatory:       Always | Conditional | Optional
  Condition:       [If Conditional] What makes it mandatory
  Type:            Data type
  Allowed Values:  [For enums] All permitted values with explanations
  Governance Owner: Who is accountable for this field's accuracy
  Immutability:    Whether the field can be changed after a rule is activated
  Population Rule: How to populate this field correctly
  Common Error:    The most frequent mistake made when populating this field
```

## 5. IDENTITY FIELDS

---

**`compliance_id`**
- Definition: Immutable system-assigned UUID that uniquely identifies this specific version of a compliance rule. Never reused. Never changed after creation.
- Layer: MASTER
- Mandatory: Always (system-generated)
- Type: UUID
- Governance Owner: System (auto-generated; human may not assign or change)
- Immutability: IMMUTABLE — never changed under any circumstances
- Population Rule: Generated by the library management system on record creation. Library Populator does not set this field.
- Common Error: Attempting to assign a human-readable ID instead of a UUID. The UUID is the system key; `compliance_code` is the human-readable key.

---

**`compliance_code`**
- Definition: Human-readable stable identifier for the compliance obligation. Used in exports, documentation cross-references, and display. Pattern: `{DOMAIN}_{SUBJECT}_{FREQUENCY}_{VARIANT}`. Examples: `GST_GSTR3B_MONTHLY_REGULAR`, `MCA_DPT3_ANNUAL`, `LABOUR_BONUS_PAYMENT_ANNUAL`.
- Layer: MASTER
- Mandatory: Always
- Type: String — pattern: `^[A-Z0-9_]{3,50}$`
- Governance Owner: Library Owner (must approve before assignment)
- Immutability: IMMUTABLE once the rule reaches `active_flag = true`. Changing the code after activation requires creating a new rule record.
- Population Rule: Propose code following the pattern. Avoid ambiguous abbreviations. All components (DOMAIN, SUBJECT, FREQUENCY, VARIANT) must be meaningful to a reader unfamiliar with the rule. The VARIANT component distinguishes variants: REGULAR vs. COMPOSITION, MONTHLY vs. QUARTERLY, SMALL_COMPANY vs. LARGE_COMPANY.
- Common Error: Using an overly abbreviated subject component that is ambiguous (e.g., `GST_RET_MONTHLY` instead of `GST_GSTR3B_MONTHLY_REGULAR`). Always spell out the subject clearly.

---

**`title`**
- Definition: Full display title as shown to end users. Must clearly identify the obligation without abbreviation. The user reading only the title should know what action is required and under which law or authority.
- Layer: MASTER
- Mandatory: Always
- Type: String, max 200 characters
- Governance Owner: Library Populator (reviewed by Domain Reviewer)
- Immutability: Mutable — may be improved for clarity without creating a new version (does not change legal meaning)
- Population Rule: Write as: "[Form Name or Action] — [Frequency] ([Authority/Law])". Examples: "GSTR-3B Monthly Return Filing — Regular Scheme (CGST Act)", "Statutory Bonus Payment — Annual (Payment of Bonus Act, 1965)". Avoid jargon or unexplained acronyms.
- Common Error: Writing an abbreviated title ("GSTR-3B Monthly") that forces the user to already know what GSTR-3B is.

---

**`short_title`**
- Definition: Compact label for calendar tiles, heat map cells, and compact list views. Maximum 60 characters. Must still be self-explanatory in context.
- Layer: MASTER
- Mandatory: Optional
- Type: String, max 60 characters
- Governance Owner: Library Populator
- Immutability: Mutable
- Population Rule: Begin with the form name or key action. Examples: "GSTR-3B Monthly", "EPF ECR Deposit", "Director KYC (DIR-3)".
- Common Error: Shortening to the point of ambiguity: "Monthly Return" (which one?), "Annual Filing" (which one?).

---

**`version_number`**
- Definition: Integer tracking how many substantive revisions this rule record has undergone. Starts at 1. Incremented each time a legal amendment, threshold change, or penalty change requires updating this record. Does not increment for cosmetic edits (typo corrections, prose improvements).
- Layer: MASTER
- Mandatory: Always
- Type: Integer ≥ 1
- Governance Owner: Library Owner (authorizes version increments)
- Immutability: Mutable (increments on substantive changes)
- Population Rule: Start at 1 for all new records. Increment by 1 whenever a substantive field (obligation, due date, applicability, consequence) changes.
- Common Error: Not incrementing on substantive changes, making it impossible to track what changed. Or incrementing for every minor edit, making the version number meaningless.

---

**`predecessor_id`**
- Definition: The `compliance_id` of the prior version of this rule, when this rule record supersedes a previous version due to a legal amendment.
- Layer: MASTER
- Mandatory: Conditional — required when this is a replacement record for an amended rule
- Type: UUID or null
- Governance Owner: Library Owner
- Immutability: IMMUTABLE once set
- Population Rule: Set when creating a new rule version that supersedes a prior version. The prior version must have `active_flag: false` and `superseded_by` pointing to this record's `compliance_id`.
- Common Error: Not setting `predecessor_id` when creating a replacement rule, breaking the version history chain.

## 6. CLASSIFICATION FIELDS

---

**`domain`**
- Definition: The top-level compliance domain this obligation belongs to. Drives dashboard grouping, domain-level filters, and domain expert assignment.
- Layer: MASTER
- Mandatory: Always
- Type: Enum
- Allowed Values (with explanation):

| Value | Meaning |
|-------|---------|
| `GST` | Goods and Services Tax obligations (returns, payments, annual reconciliation) |
| `INCOME_TAX` | Income Tax obligations excluding TDS/TCS (ITR, tax audit, advance tax) |
| `TDS` | Tax Deducted at Source — deduction, deposit, and return obligations |
| `TCS` | Tax Collected at Source — collection, deposit, and return obligations |
| `MCA_COMPANY` | Ministry of Corporate Affairs obligations for companies (AOC-4, MGT-7, DPT-3, etc.) |
| `MCA_LLP` | MCA obligations for Limited Liability Partnerships (Form 8, Form 11) |
| `SECRETARIAL` | Governance and secretarial obligations (board meetings, AGM, resolutions) |
| `EPF` | Employees' Provident Fund obligations |
| `ESI` | Employees' State Insurance obligations |
| `PROFESSIONAL_TAX` | State-level professional tax (employer and employee registration, payment) |
| `SHOPS_ESTABLISHMENTS` | Shops & Establishments Act registration and renewals |
| `FACTORIES` | Factories Act registration and compliance |
| `LABOUR_BONUS` | Payment of Bonus Act obligations |
| `LABOUR_GRATUITY` | Payment of Gratuity Act obligations |
| `LABOUR_MINIMUM_WAGES` | Minimum Wages Act obligations |
| `LABOUR_CONTRACT` | Contract Labour (Regulation and Abolition) Act obligations |
| `FSSAI` | Food Safety and Standards Authority of India licensing |
| `MSME` | MSME-related obligations (Udyam registration, Form I reporting) |
| `CUSTOMS_IEC` | Import Export Code and Customs-related compliance |
| `ENVIRONMENT` | Environmental compliance (consent to operate, hazardous waste) |
| `BOOKS_RECORDS` | Statutory books of account and record maintenance |
| `AUDIT_STATUTORY` | Statutory audit requirements under company or LLP law |
| `AUDIT_TAX` | Tax audit requirements under Income Tax Act |
| `ADVANCE_TAX` | Advance Tax installment obligations |
| `OTHER` | Obligations not falling into any of the above categories |

- Governance Owner: Library Owner (domain taxonomy changes require Library Owner approval)
- Common Error: Using `OTHER` instead of finding the correct domain. `OTHER` is reserved for genuine edge cases.

---

**`obligation_type`**
- Definition: The nature of the required action. Drives how the system presents the obligation (e.g., RETURN_FILING items are shown with filing deadlines; RECORD_KEEPING items are shown as ongoing obligations).
- Layer: MASTER
- Mandatory: Always
- Allowed Values:

| Value | Meaning |
|-------|---------|
| `REGISTRATION` | One-time act of registering under a statute (GST registration, EPFO registration) |
| `RETURN_FILING` | Periodic submission of a return/form to a government authority |
| `TAX_PAYMENT` | Periodic payment of tax, fee, contribution, or duty |
| `RECORD_KEEPING` | Maintaining statutory registers, books of account, or records |
| `GOVERNANCE` | Corporate/LLP governance action (board meeting, AGM, resolution, KYC) |
| `EVENT_BASED` | Obligation triggered by a specific business event (director change, share allotment) |
| `AUDIT` | Statutory or tax audit requirement |
| `DISCLOSURE` | Mandatory public or regulatory disclosure |
| `RENEWAL` | Periodic renewal of a license, registration, or certificate |
| `CERTIFICATE` | Issuance of a certificate to an employee, counterparty, or authority |
| `INDICATOR` | Awareness flag — no action is tracked; shows as an informational item |

- Governance Owner: Library Populator (confirmed by Domain Reviewer)
- Common Error: Using `INDICATOR` for an obligation that actually has a filing requirement. `INDICATOR` is for awareness flags (e-invoicing applicability, 43B(h) risk, 206AB check) where there is no single due date to track.

---

**`frequency_type`**
- Definition: How often the obligation recurs. Drives instance generation frequency.
- Layer: MASTER
- Mandatory: Always
- Allowed Values:

| Value | Instances Per Year |
|-------|-------------------|
| `ONE_TIME` | 1 (in the year first applicable) |
| `MONTHLY` | 12 |
| `QUARTERLY` | 4 |
| `HALF_YEARLY` | 2 |
| `ANNUAL` | 1 |
| `EVENT_BASED` | Variable (0 until event; 1 per event occurrence) |
| `CONTINUOUS` | 0 (no instances; shows as ongoing obligation) |
| `AS_APPLICABLE` | Variable (depends on specific triggering conditions) |

- Governance Owner: Library Populator (confirmed by Domain Reviewer)
- Common Error: Using `EVENT_BASED` for obligations that occur every year but are tied to an annual event (like AGM). Use `ANNUAL` for annual obligations; `EVENT_BASED` is for obligations triggered by unpredictable, non-recurring events (director resignation, share allotment).

---

**`jurisdiction`**
- Definition: Whether the obligation arises under central law (applies to all states), state law that applies to all states uniformly, or is specific to one or more named states.
- Layer: MASTER
- Mandatory: Always
- Allowed Values:

| Value | Meaning |
|-------|---------|
| `CENTRAL` | Central law applicable uniformly across India (CGST, Income Tax, Companies Act, EPF, etc.) |
| `ALL_STATES` | State-level obligation that exists in every state, but each state has its own version |
| `SPECIFIC_STATES` | Applies only to the states listed in `applicable_states` |

- Governance Owner: Library Populator (confirmed by Domain Reviewer)
- Common Error: Using `ALL_STATES` for Professional Tax (which does NOT apply in all states) or Shops & Establishments (where coverage and requirements vary significantly by state). Use `SPECIFIC_STATES` for obligations that apply in a defined subset of states.

## 7. LEGAL BASIS FIELDS

---

**`governing_act`**
- Definition: Full official name of the primary Act from which the obligation arises.
- Layer: MASTER
- Mandatory: Always
- Type: String
- Immutability: IMMUTABLE once rule is activated
- Population Rule: Use the full official name exactly as it appears in the Act or Gazette. Examples: "Central Goods and Services Tax Act, 2017", "Payment of Bonus Act, 1965", "Companies Act, 2013". Do not abbreviate.
- Common Error: Using abbreviated names ("GST Act") or unofficial names ("Bonus Act"). The full official name is required.

---

**`operative_legal_text`**
- Definition: The verbatim quoted key sentence or clause from the primary provision that creates the obligation. Must be an exact quote from the official source text, enclosed in quotation marks.
- Layer: MASTER
- Mandatory: Always
- Type: String (verbatim quote)
- Immutability: IMMUTABLE once rule is activated
- Population Rule: Copy the text exactly, preserving numbering, punctuation, and provisos. Example: `"Every registered person shall furnish, for every calendar month or part thereof, a return, electronically, of outward supplies of goods or services or both effected during such month..."` (Section 39(1), CGST Act). Do not paraphrase.
- Common Error: Paraphrasing or summarizing instead of quoting verbatim. The verbatim text is the legal anchor for the rule — paraphrasing it introduces the Library Populator's interpretation into what should be a pure factual field.

---

**`description_plain`**
- Definition: Plain-language explanation of what the obligation requires. Written for a non-legal business owner. Must explain: what must be done, who must do it, and approximately by when.
- Layer: MASTER
- Mandatory: Always
- Type: String
- Immutability: Mutable (prose improvements do not create a new version)
- Population Rule: Write as if explaining to a business owner with no legal background. Use simple sentences. Avoid statutory language. Example: "Every business registered under GST and filing monthly returns must submit Form GSTR-3B summarising its sales, purchases, and tax liability for each month, and pay any tax due, by the 20th of the following month."
- Common Error: Writing a legal summary instead of a plain-language description. Plain means business-reader plain, not professional-reader plain.

---

## 8. APPLICABILITY FIELDS

---

**`entity_types_applicable`**
- Definition: Array of entity types to which this obligation may apply. If no entity type restriction exists, use `["ALL"]`.
- Layer: MASTER
- Mandatory: Always
- Type: Array of enum values
- Allowed Values: `PROPRIETORSHIP`, `PARTNERSHIP`, `LLP`, `PRIVATE_LIMITED`, `PUBLIC_LIMITED`, `OPC`, `SECTION8_COMPANY`, `ALL`
- Governance Owner: Library Populator (confirmed by Domain Reviewer)
- Population Rule: Determine from the statute who the obligation applies to (see C2, Step 3). "Every company" = `["PRIVATE_LIMITED", "PUBLIC_LIMITED", "OPC", "SECTION8_COMPANY"]` (NOT LLP). "Every person" = `["ALL"]`. "Every employer" (under EPF) = `["ALL"]` with the employee-count threshold handled in the applicability rule expression.
- Common Error: Including LLP in Company Act obligations (LLPs are governed by the LLP Act, not Companies Act). Or using `["ALL"]` for an obligation that the statute explicitly limits to companies.

---

**`threshold_fields_involved`**
- Definition: List of `business_profile` field names that are evaluated in the applicability rule expression. Used by the UI to prompt users to answer these questions and to explain which profile facts drove the applicability determination.
- Layer: MASTER
- Mandatory: Always
- Type: Array of field name strings
- Governance Owner: Library Populator
- Population Rule: List every `business_profile` field name that appears in a condition node in the `applicability_rule_expression`. Example for GSTR-3B Monthly: `["gst_registered", "gst_scheme", "gst_filing_frequency"]`. Example for EPF ECR: `["pf_registered", "employee_count", "employee_count_band"]`.
- Common Error: Listing fields that are not actually referenced in the rule expression, or omitting fields that are. This list must exactly match what the rule expression evaluates.

---

## 9. TIMING FIELDS

---

**`due_date_determinability`**
- Definition: Whether the due date for this obligation can be computed from the rule alone (without needing user-supplied event dates or unsupported timing information).
- Layer: MASTER
- Mandatory: Always
- Allowed Values:

| Value | Meaning |
|-------|---------|
| `COMPUTABLE` | Due date can be computed from the due_date_rule without user input |
| `EVENT_DEPENDENT` | Requires a user-supplied event date (director appointment date, share allotment date) |
| `AGM_DEPENDENT` | Requires actual AGM date; can fall back to AGM legal deadline |
| `CONTINUOUS` | No single due date; obligation is ongoing |
| `PERIOD_UNKNOWN` | Timing obligation exists but cannot be encoded (delegated to future notification, etc.) |

- Governance Owner: Library Populator (confirmed by Domain Reviewer)
- Common Error: Setting `COMPUTABLE` for an event-based rule. If the due date cannot be computed without knowing when an event occurred, it is `EVENT_DEPENDENT`, not `COMPUTABLE`.

---

**`due_date_formula_plain`**
- Definition: Plain-language description of how the due date is computed. Must be understandable by a non-technical person.
- Layer: MASTER
- Mandatory: Always
- Type: String
- Immutability: Mutable (improvements do not create a new version)
- Population Rule: Write as a clear English sentence. Examples: "20th of the calendar month following the return period.", "Within 30 days of the date of appointment of a new director.", "November 30 of the same year (8 months from March 31 year-end)."
- Common Error: Restating the `rule_type` enum instead of explaining it in human terms ("OFFSET_FROM_PERIOD_END with offset 20" is not a formula plain).

---

**`extension_possible`**
- Definition: Whether the government has legal authority to extend this due date via notification or circular. TRUE does not mean an extension has been granted — it means an extension CAN be granted.
- Layer: MASTER
- Mandatory: Always
- Type: Boolean
- Population Rule: Set to TRUE for virtually all CBIC, CBDT, and MCA filings (the relevant statutes typically grant this power). Set to FALSE only where the statute explicitly makes the due date final (rare).
- Common Error: Setting FALSE by default because "extensions are not guaranteed." The field records statutory power, not current extension status.

---

## 10. CONSEQUENCE AND SEVERITY FIELDS

---

**`consequence_summary`**
- Definition: One or two sentence plain-language description of the direct consequences of non-compliance. Must reference only confirmed statutory consequences. Must not overstate or fabricate.
- Layer: MASTER
- Mandatory: Mandatory for RETURN_FILING, TAX_PAYMENT, REGISTRATION, GOVERNANCE obligation types. Optional for INDICATOR and RECORD_KEEPING.
- Type: String
- Governance Owner: Library Populator (confirmed by Domain Reviewer)
- Population Rule: State the consequence clearly. Example: "Late filing attracts a fee of ₹50 per day (₹25 for nil returns), subject to a maximum of ₹10,000 per return, under Section 47 of the CGST Act, 2017. Interest at 18% per annum applies on any unpaid tax liability under Section 50." Do not add consequences not in the statute.
- Common Error: Adding "may result in license cancellation" or "could lead to business closure" without citing the specific provision that creates this risk. If the consequence is operational (not directly statutory), it belongs in `penalty_record.blocks_description` or `registration_risk_description`, not in the main consequence summary.

---

**`base_severity_score`**
- Definition: Pre-computed severity score from 0 to 100, derived from the penalty record using the scoring model in C6. Stored for performance (to avoid recomputing on every page load).
- Layer: MASTER
- Mandatory: Mandatory when `penalty_record_id` is populated
- Type: Integer, 0–100
- Governance Owner: Computed from penalty_record fields per C6 formula. Must be recomputed whenever the penalty record changes.
- Common Error: Manually assigning a score that "seems right" rather than computing it from the C6 formula. The score must be derived from the structured penalty data, not estimated.

---

**`severity_band`**
- Definition: Categorical label derived from `base_severity_score`. See C6 Section 5 for the score-to-band mapping.
- Layer: MASTER
- Mandatory: Mandatory when `base_severity_score` is populated
- Allowed Values: `LOW` (0–19), `MODERATE` (20–39), `HIGH` (40–59), `SEVERE` (60–79), `CRITICAL` (80–100)
- Common Error: Assigning a severity band manually without computing the base score first, or assigning based on intuition ("this seems like a HIGH risk") rather than the scoring model.

---

## 11. LIFECYCLE AND TRUST FIELDS

---

**`validation_state`**
- Definition: The trust and confidence state of this rule record. Full taxonomy defined in C8.
- Layer: MASTER
- Mandatory: Always
- Allowed Values: `DRAFT`, `PENDING_PRIMARY_CONFIRMATION`, `PARTIALLY_VALIDATED`, `VALIDATED_PRIMARY`, `VALIDATED_SECONDARY`, `CONFLICTING_SOURCES`, `HUMAN_REVIEW_REQUIRED`, `SUPERSEDED`, `DEFERRED`
- Governance Owner: Library Owner (only the Library Owner may promote a rule to VALIDATED_PRIMARY or SUPERSEDED)
- Immutability: Mutable (transitions per C8 state transition map)
- Common Error: Setting `VALIDATED_PRIMARY` before the QA checklist (C12) has been completed. The QA checklist completion is a prerequisite for VALIDATED_PRIMARY, not a parallel step.

---

**`source_confidence_level`**
- Definition: Overall confidence in the quality and currency of the primary source supporting this rule.
- Layer: MASTER
- Mandatory: Always
- Allowed Values:

| Value | Meaning |
|-------|---------|
| `HIGH` | Primary source text confirmed from official channel; URL verified; provision current and unambiguous |
| `MEDIUM` | Source likely correct; some inference required; full text not retrieved or minor ambiguity present |
| `LOW` | Based primarily on secondary sources; primary source not retrieved; significant uncertainty |

- Governance Owner: Library Populator (confirmed by Domain Reviewer)
- Population Rule: Assign conservatively. When in doubt between HIGH and MEDIUM, assign MEDIUM. A rule may only have `source_confidence_level = HIGH` if the primary source text was actually read in full.
- Common Error: Assigning HIGH based on the rule being "well-known in practice" rather than on actual source retrieval and verification.

---

**`interpretation_ambiguity_flag`**
- Definition: Whether there is unresolved interpretive ambiguity in how this rule's obligation, applicability, or due date should be understood.
- Layer: MASTER
- Mandatory: Always
- Type: Boolean
- Population Rule: Set TRUE when: (a) the statute's wording is genuinely unclear, (b) two plausible interpretations exist, (c) there is a known divergence between what the statute says and what the portal/department accepts, or (d) the obligation's scope is disputed among professionals. Setting this flag is not an admission of error — it is accurate disclosure.
- Common Error: Setting FALSE to avoid the discomfort of admitting ambiguity. Undisclosed ambiguity in a rule is more harmful than disclosed ambiguity.

---

**`requires_human_review`**
- Definition: Whether a professional reviewer must assess this rule before it is actionable for a specific business. When TRUE, the system prompts the user to consult a professional before relying on this obligation's applicability determination.
- Layer: MASTER
- Mandatory: Always
- Type: Boolean
- Population Rule: Set TRUE for: foreign ownership/FEMA compliance, regulated sector obligations, complex transfer pricing, highly ambiguous provisions, and any rule in `HUMAN_REVIEW_REQUIRED` validation state. Also set TRUE when `interpretation_ambiguity_flag = true` and the ambiguity affects applicability.
- Common Error: Setting FALSE because "most businesses can handle this themselves." The `requires_human_review` flag reflects the rule's complexity and ambiguity, not the typical user's capability.

---

**`active_flag`**
- Definition: Whether this rule is part of the currently active library. FALSE for: archived (superseded), deferred, draft, and partially validated rules that have been temporarily withdrawn from display.
- Layer: MASTER
- Mandatory: Always
- Type: Boolean
- Governance Owner: Library Owner (only the Library Owner may set `active_flag: true`)
- Common Error: Setting `active_flag: true` before the QA checklist and Library Owner activation steps are complete.

---

**`review_due_by`**
- Definition: The date by which the next substantive review of this rule must be completed. Computed as `last_reviewed_at + review_interval`. Review interval: 90 days for rate/threshold/notification-based rules; 180 days for stable statutory provisions with no expected changes.
- Layer: MASTER
- Mandatory: Always
- Type: Date
- Population Rule: Assign based on the rule's change sensitivity. Rules with threshold amounts that change via notification (e-invoicing, GSTR-9 exemption) → 90 days. Rules under stable Acts (Payment of Bonus, EPF base obligation) → 180 days.
- Common Error: Setting a uniform 90-day review for all rules, creating an unsustainable review workload for stable rules. Or setting a 180-day review for notification-based thresholds that change every few months.

**Frequency Type Enum:** ONE_TIME, MONTHLY, QUARTERLY, HALF_YEARLY, ANNUAL, EVENT_BASED, CONTINUOUS, AS_APPLICABLE

**Entity Type Enum:** PROPRIETORSHIP, PARTNERSHIP, LLP, PRIVATE_LIMITED, PUBLIC_LIMITED, OPC, SECTION8_COMPANY, ALL

**Activity Type Enum:** SERVICE, TRADING, MANUFACTURING, MIXED, ALL

**Jurisdiction Enum:** CENTRAL, ALL_STATES, SPECIFIC_STATES

**Severity Band Enum:** LOW, MODERATE, HIGH, SEVERE, CRITICAL

**Source Confidence Enum:** HIGH, MEDIUM, LOW

**Validation State Enum:** DRAFT, PENDING_PRIMARY_CONFIRMATION, PARTIALLY_VALIDATED, VALIDATED_PRIMARY, VALIDATED_SECONDARY, CONFLICTING_SOURCES, HUMAN_REVIEW_REQUIRED, SUPERSEDED, DEFERRED

**Due Date Determinability Enum:** COMPUTABLE, EVENT_DEPENDENT, AGM_DEPENDENT, CONTINUOUS, PERIOD_UNKNOWN

## 13. What Should Be Deferred

**Automated field validation** — database-level constraints and application-layer validation enforcing this dictionary's rules — is a Phase 2 library management system enhancement. For MVP, conformance with this dictionary is enforced via the QA checklist (C12) and the Library Owner review gate.

**Inter-field consistency rules** — for example, automatically verifying that all field names listed in `threshold_fields_involved` actually appear as condition fields in the linked `applicability_rule_expression` — are Phase 2 tooling features.

**Deprecation of enum values** — removing a value from an allowed values list when it is no longer in use — requires a migration of all records currently using that value. This is a Phase 2 database maintenance operation.

---

## 14. Recommended Conclusion

This data dictionary establishes precise, unambiguous definitions for every field in the master library. The most important governance discipline it enforces is immutability of identity fields (`compliance_id`, `compliance_code`, `operative_legal_text`) after activation, combined with careful stewardship of the `validation_state` and `active_flag` fields as the primary controls on what users see.

Library Populators should treat this dictionary as their primary reference during the encoding phase (C10 Phase 4). Domain Reviewers should treat it as their checklist for reviewing field-level accuracy. The Library Owner is accountable for ensuring the dictionary itself is kept current as the library evolves.
